# Tickety API

Fastify + PostgreSQL. Вход — через подпись Telegram `initData`, паролей нет.

## Локальный запуск

```bash
cd server
npm install
copy .env.example .env   # заполните BOT_TOKEN
npm run dev              # http://127.0.0.1:8787
```

Без `DATABASE_URL` используется **PGlite** — настоящий PostgreSQL внутри Node,
данные в `server/.data/`. На хостинге задайте `DATABASE_URL` обычного PostgreSQL.

На чистой базе событий нет — их заводит администратор. Для локальной разработки
есть демо-события из `shared/catalog.js`:

```bash
npm run seed:demo        # уже добавленные пропускаются; в production не запускается
```

Приложение ходит на сервер, если при сборке задан `VITE_API_URL`
(локально — в `.env.development.local` в корне проекта).

### Разработка в браузере без Telegram

В браузере нет подписи Telegram. Для локальной отладки:

- `server/.env`: `ALLOW_DEV_AUTH=1`
- `.env.development.local`: `VITE_DEV_USER_ID=1001`

Тогда запросы идут с заголовком `Authorization: dev 1001`.
С `NODE_ENV=production` сервер с `ALLOW_DEV_AUTH=1` **не запустится**.

### Администраторы

`server/.env`: `ADMIN_IDS=<telegram id>,<telegram id>`. У них в «Профиле» появляется «Админка»:
события с прайсом зон, снятие объявлений с причиной, блокировка продавцов.
Права задаются только на сервере — через API их не выдать. Действия пишутся в `admin_actions`.

## API

| Метод | Путь | Доступ | Что делает |
|---|---|---|---|
| GET | `/api/health` | все | Проверка сервера и базы |
| GET | `/api/me` | Telegram | Текущий пользователь; создаётся при первом входе |
| GET | `/api/events` | все | Опубликованные события с прайсом зон (прошедшие — ещё неделю) |
| GET | `/api/listings` | все | Активные объявления (с `own: true` для своих, если вошли) |
| GET | `/api/me/listings` | Telegram | Мои объявления, включая снятые |
| POST | `/api/me/phone` | Telegram | Подтверждение номера: `{ response }` из `WebApp.requestContact` |
| POST | `/api/ticket-checks` | Telegram + номер | multipart `eventId` + `file`: формат и дубли файла → `{ checkId, fileKind }` |
| POST | `/api/listings` | Telegram + номер | `{ checkId, zone, price, quantity, sector?, row?, seat? }` → объявление |
| POST | `/api/listings/:id/withdraw` | Telegram (владелец) | Снять с продажи |
| GET | `/api/admin/events` | админ | Все события, включая скрытые, с числом билетов в продаже |
| POST | `/api/admin/events` | админ | Новое событие: поля + `zones: [{ label, nominal, seating: free|seats|sector }]` |
| PUT | `/api/admin/events/:id` | админ | Правка целиком; зоны с `id` обновляются, зону с билетами в продаже не удалить (`409`) |
| GET | `/api/admin/listings?status=active|removed` | админ | Очередь модерации с данными продавца |
| POST | `/api/admin/listings/:id/remove` | админ | `{ reason }` — снять объявление, причину видит продавец |
| POST | `/api/admin/users/:id/block` | админ | `{ reason }` — запретить продавать и снять все его объявления |
| POST | `/api/admin/users/:id/unblock` | админ | Вернуть право продавать (снятые объявления не возвращаются) |

### Что сервер не доверяет клиенту

- **Формат файла** — по сигнатуре (первым байтам): PDF, JPEG, PNG, WebP, HEIC. Имя и MIME от клиента не важны.
- **Номинал** — из прайса зоны события (таблица `event_zones`, заводит администратор). Правка прайса не меняет номинал уже выставленных объявлений. Зону и места указывает продавец; поля `nominal` в API нет, лишние поля в теле — `400`.
- **Цена ≤ номинала** — проверяет сервер, и дополнительно ограничение `price_not_above_nominal` в базе.
- **Дубли** — один и тот же файл (SHA-256) может быть только в одном активном объявлении (уникальный индекс). Это проверка файла, а не штрихкода: другой скриншот того же билета пройдёт.
- **Продавец** — только с номером, подтверждённым подписью Telegram и не заблокированный; новый продавец — до 3 активных объявлений.
- **Чужое** — чужую проверку не использовать, чужое объявление не снять (`404`).

Файлы билетов сохраняются в `server/.data/uploads/<sha256>.<ext>` (`UPLOAD_DIR`).
На хостинге нужен постоянный диск или объектное хранилище (S3).

Штрихкод с организатором пока не сверяется, и приложение этого не обещает: в интерфейсе
«файл проверен» и «продавец подтверждён», без «проверки ИИ». Сверка с организатором — позже.

Авторизация: `Authorization: tma <initData>` — строка `Telegram.WebApp.initData` как есть.
Сервер проверяет HMAC-подпись токеном бота и свежесть `auth_date` (по умолчанию сутки).

## Миграции

SQL-файлы в `migrations/` применяются по порядку при старте, каждый один раз
(учёт — таблица `schema_migrations`). Новая миграция — новый файл `002_….sql`;
старые файлы не редактируются.
