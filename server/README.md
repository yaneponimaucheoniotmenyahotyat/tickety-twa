# Tickety API

Fastify + PostgreSQL. Вход — через подпись Telegram `initData`, паролей нет.

## Локальный запуск

```bash
cd server
npm install
copy .env.example .env   # заполните BOT_TOKEN
npm run dev              # http://127.0.0.1:8787
```

Без `DATABASE_URL` используется **PGlite** — настоящий PostgreSQL внутри Node,
данные в `server/.data/`. На хостинге задайте `DATABASE_URL` обычного PostgreSQL.

На чистой базе событий нет — их заводит администратор. Для локальной разработки
есть демо-события из `shared/catalog.js`:

```bash
npm run seed:demo        # уже добавленные пропускаются; в production не запускается
```

Приложение ходит на сервер, если при сборке задан `VITE_API_URL`
(локально — в `.env.development.local` в корне проекта).

### Разработка в браузере без Telegram

В браузере нет подписи Telegram. Для локальной отладки:

- `server/.env`: `ALLOW_DEV_AUTH=1`
- `.env.development.local`: `VITE_DEV_USER_ID=1001`

Тогда запросы идут с заголовком `Authorization: dev 1001`.
С `NODE_ENV=production` сервер с `ALLOW_DEV_AUTH=1` **не запустится**.

### Команда и права

- **Владелец** — `server/.env`: `ADMIN_IDS=<telegram id>,…`. Всё, включая вкладку «Команда». Через API владельцем не стать.
- **Модератор** — события (создать, править, снять с витрины, удалить) и модерация объявлений; видит жалобы.
- **Поддержка** — обращения пользователей.

Роли выдаёт и забирает владелец в «Админка → Команда» (человек должен хотя бы раз открыть Tickety).
Права проверяются на каждом запросе — снятая роль действует сразу. Участника команды нельзя заблокировать.
Действия пишутся в `admin_actions`.

### Уведомления бота

Новое обращение → владельцам и поддержке (жалобы — ещё и модераторам). Ответ команды → пользователю.
Если пользователь не запускал бота, сообщение просто не доставится — ответ всё равно виден в приложении.
`KEEP_REJECTED=1` (только вне production) — сохранять файлы без кода в `.data/rejected` для отладки распознавания.

### Остановка и снимки базы

Локальную базу PGlite **нельзя убивать** во время записи (`taskkill /F`, «Завершить задачу») — её журнал
повреждается, и база не открывается. Останавливайте так:

```bash
npm run stop       # сервер сам закроет базу и выйдет
```

При каждом запуске сервер кладёт снимок базы в `server/.backups/` (последние 7). Восстановление —
`new PGlite(<пустая папка>, { loadDataDir: <снимок .tar.gz> })`.

### Ручной режим оплаты (PAYMENTS_MODE=manual)

Временный способ запустить продажи без платёжного сервиса: покупатель переводит деньги владельцу
по `PAYMENT_DETAILS` с кодом заказа в комментарии и жмёт «Я перевёл»; владелец в «Админка → Сделки →
Оплата» отмечает «Деньги пришли» — дальше удержание как обычно. Выплаты: продавец оставляет заявку
(перевод по СБП только на свой подтверждённый номер), владелец переводит и жмёт «Перевёл».
Подтверждать деньги может только владелец (право `payments`), не модераторы.

Риски для владельца: приём денег за чужие билеты без ИП и лицензии — серая зона; банк может
заблокировать карту по 115-ФЗ при регулярных переводах от незнакомых людей. Это мост до договора
с сервисом «Безопасной сделки».

### Оплата (бета: тестовые деньги)

`PAYMENTS_MODE=test` (по умолчанию вне production) — покупка с удержанием денег работает целиком,
но платёж тестовый: деньги не списываются, вывод — отметка. `off` — покупка выключена.
Настоящих денег сервер не принимает: держать чужие деньги может только платёжная организация,
поэтому для продакшна нужен договор с сервисом «Безопасной сделки» (ЮKassa, Т-Банк и т. п.),
и он встанет на место тестового провайдера в `src/orders.js`.

Жизненный цикл заказа: `pending` (бронь 15 мин) → `paid` (деньги удерживаются до суток после начала)
→ `completed` (продавцу: подтверждение прохода или срок без спора) | `disputed` → решение команды:
`refunded` или `completed`. Каждое движение денег — проводки в `ledger_entries` с нулевой суммой.

### Что сервер не доверяет клиенту

- **Формат файла** — по сигнатуре (первым байтам): PDF, JPEG, PNG, WebP, HEIC. Имя и MIME от клиента не важны.
- **Номинал** — из прайса зоны события (таблица `event_zones`, заводит администратор). Правка прайса не меняет номинал уже выставленных объявлений. Зону и места указывает продавец; поля `nominal` в API нет, лишние поля в теле — `400`.
- **Цена ≤ номинала** — проверяет сервер, и дополнительно ограничение `price_not_above_nominal` в базе.
- **Код входа** — на файле должен быть QR, Aztec, PDF417, DataMatrix или штрихкод Code128/ITF (`src/ticketCodes.js`: фото декодируется, PDF рендерится — до 4 страниц). Нет кода — `422`. HEIC сервер не читает (`415`), приложение переводит его в JPEG само.
- **Дубли** — по содержимому кода (отпечаток SHA-256, сам код не храним) и по файлу: тот же билет не выставить второй раз даже другим скриншотом. Уникальный индекс `listing_codes_hash` ловит и гонку; коды освобождаются триггером, когда объявление уходит из продажи.
- **Количество** — не больше числа разных кодов в файле.
- **Продавец** — только с номером, подтверждённым подписью Telegram и не заблокированный; новый продавец — до 3 активных объявлений.
- **Чужое** — чужую проверку не использовать, чужое объявление не снять (`404`).

Файлы билетов сохраняются в `server/.data/uploads/<sha256>.<ext>` (`UPLOAD_DIR`).
На хостинге нужен постоянный диск или объектное хранилище (S3).

Код с организатором пока не сверяется, и приложение этого не обещает: в интерфейсе «есть QR-код»
и «продавец подтверждён». Нарисованный код проверку пройдёт — от этого защищают подтверждённый номер,
модерация и (позже) сверка с организатором.

Авторизация: `Authorization: tma <initData>` — строка `Telegram.WebApp.initData` как есть.
Сервер проверяет HMAC-подпись токеном бота и свежесть `auth_date` (по умолчанию сутки).

## Миграции

SQL-файлы в `migrations/` применяются по порядку при старте, каждый один раз
(учёт — таблица `schema_migrations`). Новая миграция — новый файл `002_….sql`;
старые файлы не редактируются.
